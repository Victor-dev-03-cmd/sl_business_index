# SLBI Bun-first performance policy — 2026-11-22
Owner directs minimizing Node.js where practical, using Bun for compatible work while preserving Next.js/Vercel, shared desktop/mobile behavior, existing UI, auth, SQL and provider correctness.

Sources reviewed: https://vercel.com/docs/functions/runtimes/bun (Bun runtime Beta, project-wide bunVersion for non-edge), https://vercel.com/docs/package-managers (lockfile detection), https://bun.sh/guides/ecosystem/nextjs (Bun build/start), https://bun.sh/docs/runtime/nodejs-compat (compatibility varies), https://web.dev/articles/vitals (real-user experience).
Decision: adopt explicit opt-in Bun commands and isolated CI; keep existing Node/npm workflow, packageManager, lockfiles and deployed runtime until measured compatibility and approved canary. Do not add bunVersion to production vercel.json yet. Existing dependencies including sharp, pg, server auth crypto, ISR/proxy, Supabase, SDKs require tests. No framework rewrite or new Hono service solely for speed. Node API imports (node:crypto etc.) are not evidence of separate Node process under Bun. Do not replace secure implementations just to avoid imports.
- bun install --frozen-lockfile; bun run dev:bun; bun run build:bun; bun run start:bun. Explicit --bun forces runtime for Next CLI; build executes existing sharp generator once.
- Compatibility CI tests frozen install, actual SSR cookie roundtrip, search benchmarks, tsc, optimized production build and existing anonymous protected route smoke using Bun. Node CI remains required comparator. Never send credentials into synthetic CI. Review output and lockfile parity before merge.
- Release gate: compare Node and Bun using equivalent workload, same region/device/network/browser, cold/warm TTFB, memory, failure rate, SSR/ISR, authenticated route refresh, uploads, callbacks, provider timeouts; real auth smoke and rollback. Vercel runtime switch is separate config release; no mass switch, one approved deployment only.
- Performance budget (targets, not measured): p75 LCP <=2.5s, INP <=200ms, CLS <=0.1 mobile and desktop; monitor TTFB and JS/CSS weight, cache hit ratio, dynamic route p95, DB query count/latency, long tasks. Record public home/search/detail/Nearby/vendor baseline before changing. Prefer server components, route-scoped lazy imports, minimal client JS, bounded/fewer DB queries, indexes checked with safe EXPLAIN, image optimization, cache public nonpersonal data only, never shared-cache private auth or wallet. Maintain accessible responsive skeletons, reduced-motion, theme latency and low-end device/network performance. Speed improvement must be measured, not promised by swapping runtimes.
