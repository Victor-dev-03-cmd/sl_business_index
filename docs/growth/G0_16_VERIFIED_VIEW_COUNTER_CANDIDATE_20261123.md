# G0-16 — Atomic verified view counter (gated candidate, not production migration)
Date: 2026-11-23 Asia/Colombo. Baseline main `8932354dd801ddf4b20a1de4248d2bfa7eba2d57`.

**Implementation candidate only. G0-03/G0-01 OPEN; foundation 0/7, GrowthOS master 0/10. This PR must never count as an approved production cutover.**

## Why
Live G0-14/15 evidence: `app/business/[slug]/BusinessDetailsClient.tsx` called server `logEvent('view')`, conditionally inserted into `business_views`, and separately invoked public `increment_business_views(uuid)` directly from the browser. The privileged old RPC allows a caller to increment another owner's unapproved business with no internal auth/status/quota check. The analytics endpoint already performs JSON/schema/origin/privacy/HMAC/rate-limit checks and calls a service-only invoker function, but that **did not guard the old direct counter**.

## Files and actual implementation
1. [`VIEW_COUNT_FORWARD_BODY.sql`](g0/release/VIEW_COUNT_FORWARD_BODY.sql) — proposed **additive**, transactional, SECURITY INVOKER / pinned `search_path=''` `public.slbi_record_verified_business_view(uuid,uuid,text,text)`. Service-role only; wraps preexisting `slbi_record_growth_event` for verified approved-listing, channel, HMAC bucket and 60/hour quota; shares the advisory event-ID lock. Rejects prior `analytics_logs.id` **before** ingest, counts view exactly once, only for approved businesses. Log + count commit atomically; failed update raises and rolls back. It adds no new persistent table and does not modify production migration history.
2. [`VIEW_COUNT_CUTOVER_BODY.sql`](g0/release/VIEW_COUNT_CUTOVER_BODY.sql) — **separate owner-approved** production privilege cutover to revoke public/anon/authenticated EXECUTE on legacy `increment_business_views(uuid)`. Verify new service function's ACL before revoke; fail-closed if wrong. **Never run in isolation or silently execute on live production.**
3. `app/api/analytics/log/route.ts` — existing origin, privacy, HMAC, 1024-byte limit and service-only ingress retained. Only for `event_type='view'` **and both server-side `G0_VERIFIED_VIEW_COUNT_ENABLED=true` plus public build-time `NEXT_PUBLIC_G0_VERIFIED_VIEW_COUNT_ENABLED=true`**, route calls the new function instead of standard event ingestion. Other event types remain on existing RPC. Both flags off by default.
4. `app/business/[slug]/BusinessDetailsClient.tsx` — when public build-time flag enabled, the view effect logs one event and then returns; **no direct old RPC and no additional user `business_views` INSERT**. When flag disabled, legacy behavior unchanged (including its known weakness); this is only a transition candidate.
5. `tests/g0/verified_view_counter.sql`, `tests/g0/verified_view_concurrency.sh`, workflow `view_counter` matrix — isolated PostgreSQL 17 fixture with synthetic vendor A/B, customer data-free; check duplicate and changed-business replay, event/log one-to-one, pending/rejected/missing listing negatives, malformed channels/buckets/null event, 60 accepted view events and denied 61st, authenticated vendor A/B analytics row isolation, service-role-only privilege, old anonymous RPC cutover, and 8 parallel duplicate requests counting exactly once. **G0-15 known-risk negative remains in the separate public_rpc matrix**.

Verify anon/auth denied, service allowed. Cached old clients may still call revoked RPC and silently fail for count; prefer no vulnerable fallback. The public flag is not a security boundary; DB revoke is.

Once old grants revoked, do **not** re-grant unsafe anonymous EXECUTE as a routine rollback; retain server verified pipeline while repairing, or accept temporary undercount. If approved maintenance rollback of function needed, preserve logs and last good grants; no destructive history manipulation. Always validate backup and rights.
- HMAC buckets and anonymous telemetry still need retention/consent validation (G0-02), and newly added SQL must pass security/DDL review; no production provider spend in this PR.
