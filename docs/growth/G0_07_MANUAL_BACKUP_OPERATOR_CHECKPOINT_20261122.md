## Owner-run backup: no Docker, no Node runtime change
Official https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore documents CLI backup plus role/schema/data/history dumps and special auth/storage/Vault handling. The native helper `scripts/g0/manual-db-backup.sh` is a separate single-snapshot PostgreSQL custom archive option for an owner-controlled Ubuntu workstation. It does NOT replace Supabase platform-specific restore steps, storage object backups, role globals, secret/config backups, or actual tested recovery. Use PostgreSQL **17** client tools, GnuPG and trusted CA certificate from Supabase dashboard. No Docker required for this archive capture; restore still needs an isolated compatible target. No production secrets in CI, GitHub, ChatGPT or shell command history. Do not reset database password simply to run this unless separately approved, because other services may depend on it.

1. In Supabase Dashboard > Connect select Session pooler (port 5432, not transaction pooler), or direct project host if IPv6 available. Create local `~/.pgpass` using a private editor, mode 0600, matching host:5432:postgres:postgres.PROJECT_REF:password (direct user postgres). Escape colons/backslashes per libpq rules. Keep outside repo; do not paste actual value anywhere. Set PGSSLROOTCERT to trusted certificate obtained separately from dashboard. Use private encrypted disk and create a private directory outside repo.
2. From repo checkout of reviewed branch, run:
   ```bash
   mkdir -m 700 -p "$HOME/slbi-private-backups"
   export PGSSLROOTCERT="$HOME/path/to/trusted-supabase-ca.crt"
   bash scripts/g0/manual-db-backup.sh '<exact-host-from-Connect>' "$HOME/slbi-private-backups"
   ```
   Confirm BACKUP only if host matches production. Enter strong independent GPG passphrase in trusted local pinentry; store recovery passphrase separately in password manager. Helper captures full logical postgres database via pg_dump over verified TLS, encrypts stream before disk, requires successful archive decode, emits ciphertext checksum and metadata only. Any dump/encryption/decode failure blocks release; do not silently omit schemas. This path has not been tested against live Supabase in this session.
3. Preserve two encrypted copies in separate owner-controlled storage; verify `sha256sum -c SHA256SUMS` in each local directory. Never upload dump or passphrase into repo/chat/CI. Archive decode is **not** a database restore.
4. Before any release, restore into a disposable owner-controlled PG17/Supabase-compatible environment isolated from production, with trusted extensions and roles. Follow official Supabase restore for managed schemas, grants, auth/storage customization, Vault root key/config, roles, migration history and storage objects; logical archive cannot alone guarantee these. Verify isolated target identity independently; never restore into production. Do not grant broad privileges or use --clean on prod. If native archive fails to restore due to managed schema permissions, use documented Supabase CLI roles/schema/data/history procedure in a trusted Docker-enabled environment, not a partial silent fallback. No paid target without separate consent. Verify counts and canonical function fingerprints, RLS/grants, synthetic A/B auth, lead/review integrity, rollback/reapply and absence of secrets in evidence. For migration-specific release require all affected tables, ACLs/functions/triggers and recovery proven; separately document platform/storage recovery limitations. No restore proof yet.
