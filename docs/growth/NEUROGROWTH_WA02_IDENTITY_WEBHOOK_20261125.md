## WA-02 implementation
- `lib/growth/agent/wa02-webhook.mjs` implements strict Meta **GET verify_token+hub.challenge** verification (constant-time token comparison and no duplicate query keys) and **POST X-Hub-Signature-256** HMAC over ORIGINAL raw body bytes with constant-time comparison, bounded payload (256 KiB). NEVER trust parsed payload before signature. Bounded WABA envelope parsing (up to 8 entries, 8 changes each, 32 text events), rejects malformed/future messages, skips stale messages older than 15 min.
- Parsed verified inbound returns **only keyed hashes** of sender, message ID and exact trimmed text under server-side `identityPepper` plus scoped WABA ID/phone-number ID/timestamp. It does NOT expose raw phone, message body, contacts or raw Meta message ID downstream, and does NOT execute user text or invoke an LLM.
- `lib/growth/agent/wa02-linking.mjs` generates cryptographically random 192-bit one-time **SLBI LINK** code (5 minute expiry) for an **injected simulated server-verified owner/business**. Only the code's HMAC is persisted in the synthetic intent. Confirmation requires a newly authenticated signed text message addressed to exact WABA and phone number, matching hash and creation time; optional pinned sender hash. Returns **synthetic_link_candidate**, never persisted/connected; requires injected `atomicConsumeVerifiedLink` callback which future production must back by single DB transaction with unique sender across tenants, one-time intent use and step-up when moving a binding.
- Signed subsequent owner message evaluates injected owner binding status, exact WABA+phone+sender hash, fresh owner scope and injected `atomicReserveMessageOnce` to deny duplicate messages; returns `synthetic_owner_message_candidate` with **agentExecuted:false / messagesSent:false**. A phone number alone NEVER authorizes a vendor action. No WhatsApp API call, no preview or messaging takes place.
- `assessReplyPolicy` is a **classification-only** candidate: Meta AI eligibility must be explicitly confirmed; recipient owner opted in; within 24h free-form reply candidate vs outside 24h only approved template; customer marketing blocked. No outbound messages.
- `tests/ml/neurogrowth-wa02-security.test.mjs` uses HMAC-signed synthetic Meta webhooks, invalid signature/tampering, unowned tenant, wrong WABA/receiver, expired/wrong link, duplicate consumption, revoked/ambiguous binding, missing RLS, message replay, Meta policy opt-in/template tests.
- `.github/workflows/neurogrowth-wa02.yml` runs executable Node22 tests and syntax. No secrets or provider network.
- `docs/growth/HANDOFF_LATEST.md` updated in same PR as required.

## Hard safety boundaries and technical gaps
1. No Meta app or WABA configured, no verified eligible number, no real WhatsApp business owner identity, no official Meta policy clearance for this Sri Lankan operation, no real incoming webhook API route, no messages sent or received in production.
2. `serverOwnerScope`, provider account, signature secrets, and DB callbacks are **simulated injected context in tests**. No live auth.getUser(), RLS, durable nonce store, rate-limit, account disconnect, WhatsApp conversation history, or step-up on binding transfer. No service-role writes, Supabase/Neon migrations or paid resources.
3. **No WhatsApp phone/ID raw data to LLM or persistence.** The synthetic HMAC fingerprints are test artifacts. In production, encryption/rotation/privacy retention/subject access and deletion plus narrowly authorized cross-tenant uniqueness checks need design and legal review.
4. WA-01 still only produces synthetic content/approval manifests, cannot authorize real execution. WA-02 signed inbound ≠ vendor approval; signed webhook shows Meta source, not owner/business rights without link, authenticated session, server-scoped RLS and per-action approval. No auto-post, email, billing, password/security or deletes.
5. Test fixtures emulate signatures with made-up keys and phone IDs, NOT a successful Meta sandbox account/number onboarding.
