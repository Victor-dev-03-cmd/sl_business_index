## Personal vendor agent design — strict separation
The vendor AI Agent is NOT the same thing as this small MLP. The MLP can score/rank bounded aggregate growth actions; future natural-language conversation and multi-step planning require a separate language/reasoning capability, grounding and a secure tool orchestrator. Initially the production G1/G2/G3/G5 rules remain authoritative and this ML-01 model is research only.

Future scalable model: ONE versioned shared set of trained weights, but a different, RLS-owner-verified context for each vendor/business request; **do not train one model per user or merge tenant data**. Never give the model unrestricted DB access or allow its outputs to authorize their own actions. Personalization comes from:
1. server fresh `auth.getUser()` and strict business owner_id/status checks;
2. only allowlisted minimum business facts, source dates and coverage (absent != zero);
3. any optional private memory persisted by business+owner with retention/consent controls;
4. private action preference and feedback where explicitly authorized;
5. ephemeral context minimization and tenant-keyed cache. Raw leads, phone, email, reviews or private documents must NOT be exported to public Colab or third-party training.

`lib/growth/agent/capabilities.ts` is a **research-only pure proposal classifier**, not a live execution endpoint. Allowed registered proposals:
- READ CANDIDATE: owned profile, GrowthScore, insights, lead priority summary, review priority summary and saved marketing campaign drafts, still require server RLS.
- DRAFT ONLY: listing edits, follow-up reminder, review reply and marketing plan; drafts must be inspected, not applied/sent.
- APPROVAL REQUIRED: exact listing edit, reminder save, review public reply publish, campaign publish. The future server MUST bind approval to action+payload+business+user+expiry and atomically consume a nonce; call actual existing APIs only after fresh auth/RLS/confirmation and durable audit.
- BLOCKED in ML-01: billing changes, account deletion and verification approval. Deny unknown/unlisted tools and cross-owner business IDs by default.
- The model cannot freely access every dashboard operation, arbitrary SQL, billing, bank payments, admin authorization or external customer messaging; every operation requires a scoped and explicitly vetted tool adapter.

**Proactive ideas / PUSH:** separate opt-in notification and digest permission (e.g. weekly, quiet hours, rate limits, one owner per suggestion). No unsanctioned WhatsApp/email or spamming. Feedback, usefulness and action completion should be measured (not asserted). Vendor retains control, explainability, ability to mute and delete personal agent context.
