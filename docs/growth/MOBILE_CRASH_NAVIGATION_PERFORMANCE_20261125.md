# Mobile browser "Aw, Snap" and slow navigation — focused performance release (2026-11-25)

## Owner symptoms and confirmed scope
Owner provided mobile Chrome screenshot with **"Aw, Snap! Something went wrong while displaying this webpage"**, occurring intermittently while browsing live production; also reports clicks taking roughly **2–3+ seconds before visible page transition**, including Home → own Business Details. An "Aw, Snap" tab crash is a **browser renderer/process failure**, not the standard Next.js error page; possible memory pressure / heavy JS / device browser failure but the screenshot alone does **not prove an exact cause** or server exception. Vercel production runtime error clusters queried over 24h returned none. Recent Hobby runtime logs may be sparse/retention-limited; absence of server errors **does not exclude client crashes**. No real Chrome crash dump, device memory trace, Lighthouse baseline or physical before/after timing has been captured yet: **do not claim the crash is 100% eliminated or sub-second RSC responses empirically proven.**

### Actual code findings in main before this PR
1. `app/components/LoadingProvider.tsx` intentionally showed a **1,000ms** boot overlay even after page mount. Only cold boot, not every in-app navigation.
2. The five-slot MobilePublicDock used `prefetch={false}` even for the authenticated vendor's selected Business Details route. Its route had no `app/business/[slug]/loading.tsx`, so server round trips could look like an inert tap.
3. `app/business/[slug]/page.tsx` called the same business read for both `generateMetadata` and the Page, with no explicit per-request memoization; then fetched gallery/services, creating extra serial work on the server.
4. `BusinessDetailsClient.tsx` eagerly instantiated LeafletMap and loaded map/tiles despite the map being down the page. Avoiding this until the map approaches viewport reduces memory/CPU/network on typical profile opens.
5. `HomePageClient.tsx` rendered a separate mobile native experience PLUS three **CSS-hidden desktop-only** sections (hero with second HeroSearch, 24 category cells, 18 featured cards) inside mobile React tree. They consumed DOM/component/effects even though hidden. This is an identifiable source of avoidable browser work, not proven sole cause of crash.
6. Hero search autocomplete previously used `onMouseDown` for click navigation, which could behave unpredictably on touch and keyboard. GPS-assisted mobile category taps did not display feedback in the category area.

## Tested engineering changes (not measured real-device benchmark)
- `app/components/RouteNavigationFeedback.tsx` + `RootClientLayout.tsx`: very small fixed, nonblocking, pointer-events-none orange top progress plus "Opening page…" shown on **same-origin navigation click**, programmatic Hero Search and GPS router.push, removed on route change / 9s failsafe; external/new-tab/hash clicks ignored. It never hijacks native Next navigation.
- `app/loading.tsx`, `app/business/[slug]/loading.tsx`: lightweight accessible route-level streaming skeletons allow prompt shell/transition **while** server data loads; no placeholder data writes. Adds a specifically recognizable Business Details placeholder with identity, gallery and contact space.
- `MobilePublicDock.tsx`: restore Next default **automatic/partial prefetch for only the vendor's owned business fifth tab** (with route loading boundary); keep other dock entries opt-out to avoid prefetching all pages on low-RAM phones.
- `LoadingProvider.tsx`: initial intentional blocking splash reduced from 1000ms to **160ms**, without modifying the actual loading fallback.
- `HomePageClient.tsx`: first render still matches SSR to prevent hydration/layout shift, then matchMedia removes **only the three desktop-only hidden React sections on mobile**; resize observer cleanups included and recreated if resizing back to desktop. The existing visible mobile home, categories, featured cards and subsequent "How Discovery Works" editorial sections stay intact. Desktop SSR, SEO markup and desktop content preserved.
- `app/business/[slug]/DeferredBusinessMap.tsx`: load Leaflet component/tiles only after IntersectionObserver approaches the existing location card (200px margin); fallback loads immediately on older browsers. Existing location pin, zoom and height preserved.
- `app/business/[slug]/page.tsx`: React `cache` per-request business lookup to reuse data across `generateMetadata` and Page without leaking across requests or altering Supabase auth.
- `HeroSearch.tsx`: touchscreen/keyboard click for suggestion results instead of only mouse-down; longer blur allowance for slow devices; progress event on router.push. `MobileHomeExperience.tsx`: immediate finding-location status when selecting category and GPS starts.
- `tests/mobileRoutePerformance.test.mjs`: static protection for all intended changes, run automatically in **Verify Next.js Build**. This protects architecture but **is not a real device crash reproduction or LCP/INP benchmark**.

**Production safety:** No DB SQL/DDL/DML, RLS, authentication changes, payment, automatic refund, provider activation, new network telemetry, third-party analytics or services. No change to GPS security/accuracy semantics. Next.js app-level route skeleton may display on most routes when awaiting server data; retains existing Nearby Explorer's own suspense view.
