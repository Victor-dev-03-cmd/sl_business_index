# SLBI Search Corrections v1.0 — Controlled Production Design

## Scope
- Tamil/Sinhala/native Unicode typo matching against curated, approved aliases.
- Latin Thanglish / Singlish phonetic normalizations only on explicitly tagged Latin aliases.
- Optional strict, single-edit **known-town** correction from curated location aliases with actual coordinates still sourced exclusively from SL_TOWNS.
- Exact keyword/category/service/location alias match always beats approximate matches.
- No database mutation, no external inference API and no changes to PostgreSQL RPC or GeoRank.
- Nearby result chips disclose **"Interpreted as"** when an approximate intent was selected.

## Implementation / runtime guarantees
- `lib/discovery/searchCorrections.ts`: bounded codepoint Levenshtein with at most 1–2 edits; Latin phonetic normalization for common digraphs, doubled vowels and letters.
- `lib/discovery/smartSearch.ts` uses approximate service/category matching only when no exact dictionary or built-in match exists. Approximate towns are attempted only after all exact place matches fail.
- Ambiguous similar names or business-brand searches are not forced into a service category; matches with another plausible canonical group within 0.08 confidence are rejected.
- Search queries longer than 64 characters, with too many words, or short ambiguous terms are never fuzzy-corrected.
- Dynamic dictionary cached by identity; 1000-alias maximum from the existing React Query fetch. Error → original static dictionary and lexical search.
- `car wash` and `car repair` remain distinct **specific service** intents. Category-only business results continue to be marked *service unconfirmed*.

## Evaluation
- `tests/searchCorrections.test.mjs`: Unicode, mixed-script, typo, phonetic, unknown-brand, ambiguous-match, adversarial service and speed cases.
- `tests/userReportedSearchEvaluation.mjs`: 12 user-provided real input phrases with manually stated intent/location expectations; reports intent accuracy and location accuracy. This is **not** business-level relevance evaluation; no user traffic history stored.
- The existing 168-query synthetic HybridSearch benchmark and all billing/auth regression CI gates remain mandatory.

## Semantic embeddings: not yet live
The current Supabase project has `pg_trgm` / PostGIS but **no installed pgvector and no verified multilingual model**. Installing `vector` alone does not create meaningful embeddings. Embedding retrieval needs:
1. Native-speaker judged Tamil/Sinhala queries (including real business-level relevance and dialect variants).
2. Verified compatible query/business text embeddings generated by the same multilingual model and model version.
3. Safe batch generation, vector storage and incremental updates for approved businesses.
4. Privacy, service costs, rate limits, timeouts, fallback, retrieval/GeoRank-fusion tuning and nDCG/precision nonregression gates.
5. Progressive activation at a measured traffic percentage rather than a blind 100% cutover.

The model is therefore **not represented as deployed**. Accuracy and latency risks are not zero. No production migration or billing provider is required for the deterministic correction release.

## Rollback
Return to previous live SHA or remove the `findIntentCorrection` / `findTownCorrection` fallback calls. Existing keyword/GeoRank/HybridSearch and database are untouched. The search correction code does not record personal data.
