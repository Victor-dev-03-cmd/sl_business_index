# Firebase Cloud Messaging — activation checklist
This release removes the standalone navbar search shortcut and replaces the notification dropdown. It prepares an opt-in FCM device flow, isolated service worker, service-only token storage, and trusted-notification delivery queue. Existing PWA service worker stays intact. The generic lock-screen message contains no personal/account information. Firebase credentials and scheduler activation are required before dispatch works.
1. In Firebase Console, add Firebase to the existing Google Cloud project (or create a dedicated project), register a Web app, enable FCM HTTP v1 and FCM Registration API if required. Generate a Web Push certificate (VAPID public key).
2. Vercel Production env: SLBI_FIREBASE_WEB_CONFIG (JSON object with apiKey, projectId, messagingSenderId, appId from Firebase web app), SLBI_FIREBASE_VAPID_PUBLIC_KEY (public key), SLBI_FIREBASE_SERVICE_ACCOUNT_JSON (server-only JSON for dedicated FCM sender), SLBI_FCM_DISPATCH_SECRET (random >=32-character secret). Never use NEXT_PUBLIC_ for server credentials. Dedicated service account needs Firebase Cloud Messaging API Admin, not project Owner. Set secrets directly in Vercel; don't send to chat.
3. After deployment and migration, put exactly SLBI_FCM_DISPATCH_SECRET in Supabase Vault as slbi_fcm_dispatch_secret. Enable pg_cron/pg_net and run the scheduler activation SQL in docs/fcm-scheduler.sql. Do not enable a scheduler before credentials and test are ready. One invocation/minute plus immediate wake-up can be activated later; queue batches up to 20, retries lease 2 min, expires in 10 min. This is a queued delivery, not guaranteed instantaneous delivery.
4. Sign in, tap Bell → Device notifications, allow the OS/browser permission. iPhone/iPad requires installed Home Screen web app (iOS/iPadOS 16.4+). Android Chrome HTTPS works with permission; OS battery, silent/Focus/DND settings affect delivery/sound. Sound is not enforceable on web.
5. Test trusted notification insert against a consenting test account, background/lock screen on Android and installed iOS, no old notification replay, read state and signout. No Firebase access is available through the current connectors; actual device delivery cannot be confirmed before credentials and scheduler setup.

## Release: notification UI and coverage
Global Sonner toaster styles apply across public/admin/vendor pages. The Firebase service worker requests persistent, audible/vibration-capable notifications; Android/iOS/browser controls lock-screen visibility and waking the display. Reopen the installed app after deployment to refresh its service worker. Foreground FCM messages trigger an inbox refresh and a generic toast. Billing V2 events are sent after verified API success via a service-only deduplicated RPC; staff recipients resolve from the existing trusted queue (latest 250 orders). Cross-database delivery is best effort, not atomic with Neon; reconciliation/outbox still needed for guaranteed recovery. Critical uncaught Node server errors alert staff; authenticated app error-boundary reports alert only the account itself; billing 5xx alerts affected account and staff. Deduplication is per recipient/category/30-minute UTC bucket. No routine form validation, raw stack traces, password errors or arbitrary client toast forwarded. Promotion decisions are published only for authorized staff updates. Device-level lock screen and screen wake must be verified on the actual mobile OS.
